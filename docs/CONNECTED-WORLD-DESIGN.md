# Shiny Village: 한 세계로 연결하는 2단계 설계안

상태: 검토용. 이 문서의 지도 통합·서버 변경은 구현하지 않았다. 이번 배포 범위는 농장 지도 안 조작과 HUD뿐이다.

## 목표 경험

내 밭에서 수확한 학생이 길을 따라 광장으로 걷고, 같은 반 친구를 만나 인사한 뒤 장터 문으로 들어가 교환한다. 별빛도서관과 여권은 현재 화면으로 연결한다. 자유 채팅·음성은 추가하지 않는다.

## 현재 코드에서 확인한 기반

| 영역 | 현재 구현 | 전환 시 처리 |
|---|---|---|
| 지도 | `farm3d.js`가 하나의 THREE.Scene에 농장과 마을을 생성한다. `farmView`가 카메라·라벨·캐릭터 표시를 바꾼다. | 장면 전체를 다시 만들기보다 구역별 표시와 이동을 분리한다. |
| 개인 농장 | 내 밭과 재고는 서버의 학생별 state에 저장한다. 작업은 저장 후 애니메이션을 보여 준다. | 소유권·저장 순서를 유지한다. 걷기 연출에 저장을 의존시키지 않는다. |
| 광장 | `plaza.js`는 요청 완료 후 약 1.1~1.25초 뒤 다시 조회한다. 목적지까지 위치를 보간한다. | 첫 시제품은 이 방식을 유지하고 통행 구역을 확장한다. |
| 위치 서버 | `src/plaza.mjs`가 학급별 위치를 조회하고 15초 지난 접속을 제외한다. 현재 이동 범위는 작은 광장이다. | `zone`과 이동 가능한 길의 범위를 검증한다. 경계 이동도 서버에서 확인한다. |
| 장터 | 도착하면 `#market`의 만남 화면을 열고, 기존 교환 API가 재고를 변경한다. | 첫 단계는 문을 지나 입장하는 연출을 유지한다. 장터 내부까지 모두 3D로 재작성하지 않는다. |
| 체험 | 광장 캐릭터는 로컬 연습 친구, 교환은 별도의 체험 학급 기록을 쓴다. | 실제 친구로 오인하지 않도록 표시하며 학급과 같은 경로를 체험한다. |

## 화면·이동 구조

`내 밭 → 농장 앞길 → 우리 반 광장 → 장터 입구 → 기존 장터 화면`

- 도로와 출입구를 실제 이동 가능한 경로로 연결한다. 장식으로만 그린 시설에는 준비 중 표시를 둔다.
- 다섯 탭은 빠른 이동 수단으로 유지한다. 지도 안에서도 걸어서 같은 목적지에 도달한다. 서로 다른 기능의 메뉴를 두 개 만드는 것이 아니라 같은 이동 명령을 호출한다.
- `#farm`, `#village`, `#market` 주소는 유지한다. 주소로 입장하거나 새로고침하면 해당 구역의 안전한 입구에 놓는다. 이동 도중 새로고침해도 작물·재고는 변하지 않는다.
- 지도 표현은 `현재 구역`, `선택한 대상`, `이동 목적지`로 구분한다. 기존 `farmView` 하나가 농장 조작과 세계 전체를 동시에 결정하는 결합을 먼저 줄인다.
- 다른 학생의 밭을 방문하는 기능은 후속 범위다. 공유하는 모습과 내 작업 권한을 분리하고, 친구의 밭에는 작업 요청을 보낼 수 없게 한다.

## 위치 조회를 먼저 유지하는 이유와 전환 기준

친구 캐릭터는 이미 목적지 보간으로 움직인다. 따라서 ‘부드러움에는 반드시 실시간 서비스가 필요하다’고 단정할 수 없다. 다른 학생이 이동을 시작했다는 사실이 보이는 지연과, 내 화면 안에서 캐릭터가 움직이는 부드러움은 다르다.

현재 간격만으로 계산하면 30명이 동시에 광장에 있을 때 초당 약 24~27회, 120명이라면 약 96~109회의 주기 요청이 발생할 수 있다. 이는 응답 시간과 추가 이동 요청을 제외한 단순 추정이며 부하 시험 결과가 아니다. 매 응답이 같은 학급의 위치 목록을 담으므로 요청 수뿐 아니라 데이터 크기와 DB 작업량도 측정해야 한다.

| 측정 결과 | 판단 |
|---|---|
| 30명에서 친구의 출발이 대부분 2초 이내에 보이고, 기존 저장·교환 응답이 악화되지 않음 | 현 조회 방식으로 1차 연결 지도를 운영한다. |
| 출발 전달이 늦지만 렌더링은 충분히 빠름 | 위치 전달 계층을 push 방식으로 교체하는 별도 시제품을 만든다. |
| 전달은 빠른데 화면 FPS가 낮음 | 통신 서비스를 교체하기보다 아바타 수·그리기 비용을 줄인다. |

특정 외부 서비스를 지금 채택하지 않는다. 필요하면 현재 인증·학급 격리를 유지할 수 있는 WebSocket 방식과 외부 실시간 서비스를 비교한다. 재접속·교사 정지·학급 간 차단 검증 없이 전환하지 않는다.

## 성능 목표와 검사 조건

- 4개 반은 각각 24~30명 공간으로 분리한다. 120명을 한 장면에 모두 그리지 않는다.
- 학교 노트북과 태블릿에서 30명 장면을 각각 측정한다. 목표는 보통 화질 30 FPS, 저사양 설정 20 FPS 이상이다. 현재 달성했다고 주장하는 수치는 아니다.
- 보이지 않는 구역의 캐릭터·라벨은 그리지 않는다. 아바타 모델과 재질을 재사용하고 이름표 수도 제한한다.
- 걷는 동안 재고·학습 기록 전체를 반복해서 전송하지 않는다. 현재의 일시적 위치 기록 분리를 유지한다.
- 실제 학교 와이파이에서 지연·끊김·탭 복귀를 시험한다. 기기당 프레임 시간, 위치 반영 지연, 서버 요청 실패율, 저장·교환 지연을 별도로 기록한다.

## 기록 보존

학생 ID, 학급 ID, 밭·재고·코인·여권·공부 기록은 변경하지 않는다. 새 지도 좌표는 재고와 분리된 일시적 접속 기록으로 다룬다. 서버 스키마 변경이 필요하면 추가 필드 방식으로 적용하고, 이전 클라이언트와 호환되는 기본값을 둔다. 실제 학생 데이터로 실험하지 않는다. 배포 전 백업·되돌리기 절차와 두 계정의 격리 검사를 확인한다.

## 작업 순서와 경계

| 단계 | 수정 범위 | 통과 기준 |
|---|---|---|
| A. 구역 분리 | 기존 장면의 구역·카메라·상호작용 상태 분리. 서버 변경 없음. | 기존 농장·광장·장터·도서관 왕복, 주소·새로고침, 밭 대상 일치 |
| B. 혼자 걷는 연결 지도 | 내 농장 앞길에서 광장까지 이동, 출입구와 카메라 전환 | 터치·방향키·마우스, 길 경계, 작업 중 이동·저장, 숨김·복귀 |
| C. 학급 친구 연결 | 광장 위치 프로토콜의 구역 확장, 정해진 인사만 제공 | 두 계정 이동과 인사, 학급 격리, 30명 부하·실기기 측정 |
| D. 필요 시 통신 교체 | C의 측정 결과가 기준 미달일 때만 별도 수행 | 재접속·부하 개선 및 재고·교환의 기존 보장 유지 |

A와 B는 현재 장면을 정리하는 작업, C는 서버와 권한 검증까지 포함하는 작업이다. 친구 농장 방문·장터 전체 3D화·자유 대화는 이 승인 범위에 넣지 않는다. 단계마다 검증한 시제품을 보여 준 뒤 다음 단계로 진행한다. 정확한 소요 기간은 A에서 결합 정도와 학교 기기 성능을 확인한 뒤 산정한다.
